# i18n with locale path prefixes

Objective: every page exists in Spanish and English under a locale prefix (`/es/...`, `/en/...`), unprefixed paths redirect to the visitor's language, and every text the user reads (HTML, JS-generated text, server errors shown to the user) follows the page language. Branch: feat/messages (the user owns git: no commits). Delivery: no commits; slices reported to the user. Test runner: `bun test` (unit), `bun run test:e2e`.

## Specs

- S1 (routes): "para esto usa i18n, siendo que todos los idiomas tienen su prefijo de ruta." Accepted design (L2): locales `es` and `en`, the same path slugs in both: `/es`, `/es/sign-in`, `/es/sign-up`, `/es/chat` and the same under `/en`.
- S2 (redirects): accepted design (L2): unprefixed paths (`/`, `/sign-in`, `/sign-up`, `/chat`) answer 302 to the chosen locale: the `lang` cookie if present, else the browser's `Accept-Language`, else `es`.
- S3 (HTML): accepted design (L2): one HTML file per page and locale, no build step or framework. An e2e test checks that both versions keep the same structure (ids, `data-*`, forms), so they do not drift apart.
- S4 (JS text): accepted design (L2): the texts the JS generates (chat, connection banners, form errors) come from a dictionary per locale, chosen by `<html lang>`. Assumption: dates use the page locale too.
- S5 (server errors): accepted design (L2): the API returns only text (no codes, verified in `http.error-response.ts`), so the client translates the known errors and shows unknown ones as they come.
- S6 (SEO): accepted design (L2): `hreflang` and `canonical` on every page, and a language switcher in the header that saves the `lang` cookie. Assumption: the switcher links to the unprefixed path with `?lang=<locale>` so it works without JS; canonical/hreflang need absolute URLs, so production injects them from the public origin (first `APP_ORIGINS` entry); `/chat` is `noindex` and gets none.
