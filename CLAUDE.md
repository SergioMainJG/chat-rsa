# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack constraints

- Runtime, bundler, test runner, linter, and formatter: **Bun canary**. `bun lint` and `bun fmt` are not in stable Bun yet (1.4.4), so local and CI both use canary. Switch CI to `latest` once they ship in stable.
- TypeScript **7.1.0-beta**, installed locally. Type checking runs through its `tsc --noEmit`.
- The only runtime dependencies allowed are `jose` (JWT) and `@zxcvbn-ts/*`. Everything else uses Bun natives: `Bun.serve` routes + HTML imports for the frontend, `Bun.password` (argon2id) for password hashing, `SQL` from `bun` for Postgres, `RedisClient` from `bun` for Valkey, and `$` for shell scripts. Do not add frameworks or ORMs.
- Frontend and backend are both vanilla TypeScript in one repo. Bun bundles the frontend from the page HTML imports in `src/backend/shared/http/app.server.ts`.

## Commands

```sh
bun install
bun run dev                 # hot-reload server (needs the pod infra running)
bun fmt                     # format; CI runs `bun fmt --check`
bun lint --max-warnings 0   # CI fails on warnings
bun run typecheck
bun run test:unit           # src/**/*.test.ts
bun run test:integration    # test/integration, needs Postgres + Valkey
bun run test:e2e            # test/e2e, starts the real server on port 0
bun run test:load smoke     # k6 (grafana/k6:2.4.0 via Podman) against a running server; `load` for the 2-minute profile
bun test path/to/file.test.ts -t "test name"   # single test
bun run verify              # fmt check + lint + typecheck + unit (same as the CI quality job)
```

Do not add `lint` or `fmt` scripts to package.json: `bun lint` runs a package.json `lint` script when one exists, so a script named `lint` that calls `bun lint` would call itself forever.

## Local infrastructure (Podman pod, no Containerfiles)

`scripts/pod.ts` builds a `chat-rsa` pod from upstream images (`postgres:18-alpine`, `valkey/valkey:9.2-alpine`, `oven/bun:canary`):

- `bun run pod:infra` starts only Postgres and Valkey (for `bun run dev` on the host and for integration/e2e tests).
- `bun run pod:up` also starts the app container, which mounts the repo.
- `pod:down`, `pod:status`, and `pod:logs` do what their names say.

Host ports default to 3001, 5433, and 6380 so they don't collide with other projects' pods. Override them with `POD_APP_PORT`, `POD_DB_PORT`, and `POD_CACHE_PORT`. All three are published on `127.0.0.1` only (Postgres uses static `chat:chat` credentials and Valkey has no password); `POD_APP_BIND=0.0.0.0` opens just the app to the LAN. Port mappings are fixed when the pod is created, so run `pod:down` before a change takes effect. The defaults in `src/backend/shared/config/env.config.ts` point at those host ports. Containers in the pod reach each other on `localhost` at the standard ports.

`sql/` is mounted into Postgres' `docker-entrypoint-initdb.d`, which only runs on an empty volume, so `main.ts` also applies `sql/index.sql` (idempotent `IF NOT EXISTS`) at startup. Sign-in tokens are HS256 JWTs signed with `JWT_SECRET`, which is required and must be at least 32 characters (put it in `.env`); there is no dev default, and only `NODE_ENV=test` (set by `bun test`) falls back to a test-only secret when it is unset. Otherwise `loadConfig` throws `JWT_SECRET must be set to at least 32 characters`.

## Production image

`Containerfile` (with `.containerignore`) builds the server image on `oven/bun:<BUN_VERSION>-alpine` (build arg, default `1.4.4`): `podman build --platform linux/amd64 -t chat-rsa .`. It runs from source as the unprivileged `bun` user with `NODE_ENV=production` and `PORT=3000`, because production bundles `src/frontend` with `Bun.build` at startup, serves `public/` and applies `sql/index.sql`; Postgres and Valkey are not in it. `CMD` uses exec form so Bun is PID 1 and gets SIGTERM for the graceful shutdown. Runtime env: `JWT_SECRET` (required), `DATABASE_URL`, `VALKEY_URL`, and `APP_ORIGINS` with the public URL first. The local pod still uses upstream images only.

## Architecture

Screaming + Clean architecture: features at the top level, Clean layers inside each feature, and files named `<feature>.<responsibility>.ts`.

```
src/
  backend/<feature>/
    domain/          ports and entities (no imports from other layers)
    application/     use cases that depend only on domain ports
    infrastructure/  adapters implementing ports (Bun SQL, RedisClient, …)
    presentation/    HTTP controllers that return Response
  backend/shared/    cross-feature config and the HTTP server factory
  backend/main.ts    composition root: builds the adapters and injects them into createServer
  frontend/<feature>/presentation/   pure view logic (unit-testable without a DOM)
  frontend/index.{es,en}.html        home page (spec: docs/design/home-page.md); home.css
  frontend/auth/                     sign-in.{es,en}.html and sign-up.{es,en}.html (served at /<locale>/sign-in and /<locale>/sign-up), auth.css, auth.form.ts (the only JS: submits the form as JSON)
  frontend/messaging/                chat.{es,en}.html (served at /<locale>/chat), crypto/, connection/, search/, application/, presentation/
                                     (below 900px the chat shows one pane; the `Rooms` and `Back to the room` buttons toggle `data-show-rooms` on `.chat` and move focus to the shown pane's heading, and openRoom clears it; `Manage room` is a `popover="auto"` anchored with `position-area` behind `@supports`)
  shared/contracts/  types shared by frontend and backend
test/
  integration/       adapters against real services (*.integration.test.ts)
  e2e/               full HTTP server (*.e2e.test.ts)
```

- Dependencies point inward: presentation → application → domain. Infrastructure implements domain ports, and only `main.ts` (or a test) wires infrastructure in.
- `createServer` takes its dependencies (port, adapters) as arguments, so e2e tests run it with `port: 0`. A new feature adds its routes there and receives its adapters from `main.ts`.
- Unit tests sit next to the file as `*.test.ts` and use fake ports, never real services.
- Route guards: guarded pages start with `<html data-guard="pending">` plus an inline `<style>` in their `<head>` that hides the body; it must stay inline (an external stylesheet can arrive after the first paint), and `test/e2e/pages.guard.e2e.test.ts` checks it. `bun --hot` does not reload edited `.html` files: restart the dev server after changing one. Their script calls `enforceAccess('members' | 'guests')` from `frontend/auth/auth.page-guard.ts` (decision in `auth/presentation/auth.guard.ts`) and `revealPage()` only when the visitor may stay; the chat reveals itself only after the server accepted the session. The guard reads only the `chat_rsa_session_hint` cookie (the token's `exp`); the JWT itself is HttpOnly. A new guarded page needs both the attribute and the call.
- Every page opens with a `.skip-link` (to `#main`; in the chat to `#composer-text`, hidden while no room is shown) and has a `<meta name="description">`; the chat is `noindex` and `public/robots.txt` disallows `/chat`, `/api/` and `/ws`. The logo is `assets/isotipo-96.webp`: Bun's HTML bundler cannot resolve `srcset` (it reads the whole list as one path), so pages use a single `src`.
- Static assets and shared styles: pages reference `public/` icons by relative path (Bun bundles them with hashed names; absolute `href="/x"` fails the bundle); `src/backend/shared/http/public-assets.ts` also serves the icons and `site.webmanifest` at the root. `src/frontend/styles.css` is loaded by every page and holds the design tokens, the system font, the site header and buttons, and the CSS cross-document view transitions (`@view-transition`, off for reduced motion; `.site-header .brand` morphs as `brand`, so each page has exactly one). Each page also has a `<link rel="expect" blocking="render">` on its above-the-fold content. Bun inlines CSS `url()` assets under 128 KB as `data:` URLs, which the CSP refuses for fonts: do not add `@font-face` files through CSS.
- i18n (spec: `odd/tasks/i18n.md`): every page exists in Spanish and English, one HTML file per locale (`*.es.html`, `*.en.html`) with the same structure (`test/e2e/pages.i18n.e2e.test.ts` compares ids, classes, `data-*` and form attributes; change both files together). Routes carry the locale: `/es`, `/es/sign-in`, `/es/sign-up`, `/es/chat` and the same under `/en`; locales and page paths live in `src/shared/i18n/i18n.locale.ts`. Unprefixed paths (`/`, `/sign-in`, `/sign-up`, `/chat`) answer 302 (`no-store`, `Vary: Cookie, Accept-Language`) to the `lang` cookie's locale, else `Accept-Language`, else `es` (`locale-redirect.ts`); the header switcher links to the unprefixed path with `?lang=<locale>`, which sets `lang` for a year. Scripts take every text from `src/frontend/i18n/i18n.messages.ts`, which reads `<html lang>` when it loads (English without a document, so unit tests read English unless they call `setLocaleFromLang`); page paths in script come from `pagePath`. The API answers errors in English only: `translateServerMessage` (`i18n.server-errors.ts`) translates the known ones where the client reads them (`auth.view.ts`, `chat.api.ts`, the room stop notice) and leaves unknown ones as they are; a new user-facing server message needs a Spanish rule there. In production `buildPages(publicOrigin)` adds absolute `canonical` and `hreflang` links (plus `x-default`, the unprefixed path) to every page but the chat, from the first `APP_ORIGINS` entry, so put the public URL first.
- Production pages: Bun's HTML-import routes hard-code their headers, so with `NODE_ENV=production` `main.ts` passes `pages: await buildPages()` (`shared/http/static-pages.ts`): the pages are bundled once at startup with `Bun.build` and served as plain routes with the security headers, precompressed brotli/gzip (`Vary: Accept-Encoding`), ETag revalidation (`no-cache`) for pages and `immutable` hashed assets; an empty entry chunk (a page without a script) is dropped with its `<script>`. Without `pages` (development and most tests) the HTML imports are served as they are. `test/e2e/pages.production.e2e.test.ts` covers it.
- Security headers: every response carries `SECURITY_HEADERS` (`shared/http/security-headers.ts`: `frame-ancestors 'none'`, `X-Frame-Options`, `nosniff`, `Referrer-Policy: no-referrer`, COOP, `Permissions-Policy`, HSTS). The few places that build a `Response` (`http.respond.ts`, `http.error-response.ts`, `user.controller.ts`, `public-assets.ts`, `static-pages.ts`) spread them in; a new one must too.
- CSP: every page (`/<locale>`, `/<locale>/chat`, `/<locale>/sign-in`, `/<locale>/sign-up`) carries its policy in `<meta http-equiv="Content-Security-Policy">` (the HTML imports cannot set headers; the header CSP in production adds only `frame-ancestors`, which a meta tag ignores): `default-src 'self'; script-src 'self'; style-src 'self' 'sha256-…'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'`. The hash is the inline guard style, byte for byte: changing that style means updating the hash in all eight pages, and `test/e2e/pages.csp.e2e.test.ts` fails until they match. No other inline script, style or `style=` attribute is allowed.
- Form fields: `src/frontend/shared/form-validity.ts` (`installFieldValidity`, once per page) keeps `aria-invalid` in step with `:user-invalid` and lists a field's error message (its id in `data-error`) in `aria-describedby` only while it is shown; never reference an error element from `aria-describedby` in markup. `flagServerError` marks a field the server refused, and the auth form then focuses the first one.
- Frontend pages lean on the platform: native constraint validation (`required`, `pattern`, `maxlength`, `autocomplete`) mirrors the server rules, and CSS (`:user-invalid`, `:empty`, `[aria-busy]`) draws every state. JS is limited to submitting forms with `fetch`, because the API accepts `application/json` only (415 otherwise, as a CSRF guard). Keep page logic that can be tested without a DOM in `frontend/<feature>/presentation/`.

## Messaging (E2EE rooms)

Spec and decisions: `odd/tasks/messages.md`. Wire contracts: `src/shared/contracts/messaging.contract.ts` (REST) and `messaging.socket.contract.ts` (WebSocket frames, close codes, subprotocol auth).

- Transport split: WebSocket `/ws` carries live messages, ACKs, typing, presence and read receipts. REST under `/api/rooms`, `/api/keys`, `/api/users` and `/api/auth/refresh` carries history, keys, membership and lookups. The composition is in `src/backend/app.composition.ts`, shared by `main.ts` and `test/e2e/messaging.e2e.test.ts`.
- Socket auth: browsers open `new WebSocket(url, ['chat-rsa.v1'])` and authenticate with the `chat_rsa_session` cookie, which needs an `Origin` in `APP_ORIGINS` (403 otherwise). Programmatic clients (tests, k6) may send `['chat-rsa.v1', 'bearer.<jwt>']` instead; the bearer wins over a cookie. The server answers only `chat-rsa.v1`. A successful `POST /api/auth/refresh` reschedules the expiry of that session's sockets and pushes `auth.refreshed { expiresAt }` (`gateway.renewSession`); bearer clients may still send an `auth.refresh` frame, and a failure closes with 4001. Heartbeat pings close a silent socket with 4008. SIGTERM drains in this order: stop upgrades, await in-flight sends, close with 1001, stop HTTP, close pools (`installShutdown` in `shared/lifecycle`).
- Ordering and idempotency: PostgreSQL generates every message id (`uuidv7()`), and `created_at` is derived from it. Clients never send ids or timestamps. `UNIQUE (sender_id, idempotency_key)` makes retries return the stored original (`duplicate: true`, no second fan-out).
- The chat keeps message entries and their page elements keyed by `<senderId>:<idempotencyKey>` (`messageKey` in `presentation/chat.view-model.ts`): idempotency keys are unique per sender only, so another member can reuse one, and a message that fails to decrypt keeps only the text that same message (same sender and id) already had.
- Receipts are per-member watermarks on `room_members` (`last_delivered_message_id`, `last_read_message_id`). They only move forward, and reading implies delivered. The client sends `read` only for messages an IntersectionObserver saw on screen.
- Room bounds 2..100: a locked counter with an immediate max check, plus a deferred min check at COMMIT. Each join/leave bumps `rooms.key_epoch`, and sends with a stale epoch are refused (409).
- E2EE (`src/frontend/messaging/crypto`): X25519 + HKDF-SHA256 + AES-256-GCM via Web Crypto only. Sender Keys use one chain key per (room, epoch, sender), wrapped per recipient with an ephemeral X25519 key. Private keys are non-extractable `CryptoKey`s in IndexedDB. The server stores only `ciphertext`/`iv`/`auth_tag`, so search runs client-side over the decrypted local store (`frontend/messaging/search`).
- Client resilience (`src/frontend/messaging/connection`): full-jitter exponential backoff (1 s base, 30 s cap), immediate reconnect on `online`, an IndexedDB outbox flushed strictly in order, one ack at a time.
- Zero-trust HTTP: `readJsonObject`/`readQuery` reject unknown keys, a wrong content type and bodies over 64 KiB; sign-in and sign-up read their body through `readCappedJsonObject` (same content type and 64 KiB cap, unknown keys left to the credentials validation). The guard in `shared/http/http.guard.ts` runs an IP token bucket, then the origin check, then the JWT (from `Authorization: Bearer`, else the `chat_rsa_session` cookie; never the hint cookie), then a user token bucket. Buckets live in Valkey (Lua script, same math as `shared/domain/token-bucket.ts`) and are configured with `RATE_LIMIT_IP_CAPACITY`, `RATE_LIMIT_IP_REFILL`, `RATE_LIMIT_USER_CAPACITY` and `RATE_LIMIT_USER_REFILL` (defaults 120/20 and 60/10). Sign-in and sign-up are behind the IP bucket too, so the k6 `stress` profile from one IP now also hits 429s.
- Client IP: the socket peer, except when the peer is in `TRUSTED_PROXY_IPS` (comma-separated, default empty; e.g. the Cloudflare tunnel's address) and `CF-Connecting-IP` holds a valid IP, which is used instead. `X-Forwarded-For` is always ignored. Every guard (`authenticated`, `public`, `session`, `upgrade`) uses it.
- CSRF: `APP_ORIGINS` (comma-separated, default `http://localhost:<PORT>,http://127.0.0.1:<PORT>`; add the public URL behind a tunnel). Any POST/PUT/PATCH/DELETE whose `Origin` is not listed answers 403 (`Origin not allowed`), and so does a cookie-authenticated unsafe request without `Origin`. Bearer clients without `Origin` still pass.
- Per-account sign-in throttle: `SignInUseCase` spends `signin:<name>` (`RATE_LIMIT_SIGNIN_CAPACITY` default 10, `RATE_LIMIT_SIGNIN_REFILL` default 1/30 per second) before the password hash is checked, for known and unknown names alike; empty means 429 with `Retry-After`. Someone can slow down sign-in for a known name (accepted tradeoff).
- Sessions: sign-in, sign-up and refresh answer `{ user }` only and set two cookies: `chat_rsa_session=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=<token lifetime>` (the credential) and `chat_rsa_session_hint=<exp seconds>` (same attributes without HttpOnly; not a credential, read only by the route guard). No token is ever in a body, `sessionStorage` or any JS-readable place, and `ChatApi` sends no `Authorization` header. Every JWT carries a `sid` and an `sst` (session start, epoch seconds) that `/api/auth/refresh` keeps; tokens without `sst` are refused, and refresh answers 401 once `now - sst > SESSION_MAX_AGE_SECONDS` (default 604800, 7 days). `POST /api/auth/sign-out` answers 204 and clears both cookies (`Max-Age=0`, also with a 401 for an invalid session), revokes the session in Valkey (`revoked-session:<sid>`, one token lifetime), `RevocationAwareTokenVerifier` refuses its tokens everywhere (fails closed), and the gateway closes its sockets with 4001 and remembers the session id for one token lifetime, so a socket of it that opens later (upgrade verified just before the sign-out) is closed with 4001 at once. The chat page's Sign out button deletes the hint cookie client-side even when the server call fails, and replaces the location with the sign-in page of its locale; per-user E2EE keys and the decrypted store stay on the device so the chat is readable after signing in again. `GET /api/rooms/:roomId/members` gives members the names of the other members.
- Room authorization: every REST route and every room frame re-checks membership through `roomOfMember`. A missing room answers like a forbidden one (403), so room ids cannot be probed.

## Load testing (k6)

`test/load/auth.load.ts` is a k6 script (k6 runs TypeScript natively; only `@types/k6` is installed, for tsc and lint). `bun run test:load [smoke|load|stress]` runs it through `test/load/k6-runner.ts` from the pinned `grafana/k6` image with `--network host` against `LOAD_BASE_URL` (default `http://localhost:$PORT`), then deletes exactly the users the run created (`^load<runId>[pum][0-9]+$`) and refills the buckets it spent (loopback `rl:ip:*`, its users' `rl:user:<id>`, and `rl:signin:load<runId>*`), even when the delete fails. It reads only `PORT`, `DATABASE_URL` and `VALKEY_URL` (`loadConnectionConfig`), never `JWT_SECRET`. k6 exits 99 when a threshold fails, and the script keeps that exit code.

- Each request declares its own expected statuses (`responseCallback`), so a 401 on a valid sign-in counts as a failed request. Never go back to a global `setResponseCallback`.
- `bun run test:load:probes` runs the scripts against `test/load/support/fake-auth-server.ts` and `fake-messages-server.ts` with one deliberate defect per case, and asserts that k6 fails exactly the check(s) that defect breaks. Add a sabotage whenever you add a check. Both fakes use the server's default rate-limit policies (IP, user, and the per-account sign-in bucket), so a script that would trip them against a real server trips them in the probes too.
- k6 2.4.0 cookies: `response.cookies` has no SameSite field (read the raw `Set-Cookie` header, which k6 joins with ", "), reports `Max-Age=0` as `max_age: -1`, and its default jar sends `Secure` cookies over `http://localhost` (a cookie-only request sends an explicit `Cookie` header with an empty `CookieJar`).
- Capacity is bounded by argon2 (`Bun.password`, argon2id, 64 MiB, t=2, p=1): about 19 operations/s on 8 cores when concurrent, at about 140 ms each. Every sign-up, sign-in, wrong-password and unknown-user check costs one operation. `load` asks for about 7/s and passes. `stress` (a 30-VU spike) saturates on purpose and fails its latency threshold (p95 about 3 s). With the IP token bucket on sign-in and sign-up (see Messaging), a single-IP spike past the burst also gets 429s; raise `RATE_LIMIT_IP_*` for load runs. The per-account sign-in throttle (10 attempts, then one per 30 s per name) is respected by walking the pool: each scenario signs in with the next pool name, and `load` uses 80 pool names, so `smoke`, a same-`RUN_ID` `smoke` rerun and `load` stay within it; `stress` still needs `RATE_LIMIT_SIGNIN_*` raised. `messages.load.ts` `stress` fits the default IP bucket (its burst starts after `live` and `rest`); its `load` profile needs `RATE_LIMIT_IP_*` raised. The scripts read the JWT from the `chat_rsa_session` cookie (`response.cookies`) and send it as `Authorization: Bearer`.

## CI

`.github/workflows/ci.yml` runs on pushes to `main`, on `v*` tags and on pull requests (a new push cancels a pull request's running run; a running `main` or tag run is never cancelled, but a newer push replaces a queued one, so a commit pushed in between may get no `sha-<short>` image). Every action is pinned to a full commit SHA with its release in a comment; bump both together. The `quality` job runs fmt check, lint, typecheck, and unit tests. After it passes, `integration` runs integration and e2e tests against Postgres and Valkey service containers. The image smoke test is `.github/scripts/image-smoke.sh <image>`: it boots the image against those services and checks that `/es` and `/en/chat` answer 200, `/` 302, pages come brotli-compressed, the process is not root, and SIGTERM exits with code 0. On pull requests, `image` (in parallel with `integration`) builds the `Containerfile` (layers cached in the GitHub Actions cache) and runs it. On pushes, `publish` runs after `integration` and is the only job with `packages: write`: it builds the image once, pushes it to `ghcr.io/<owner>/<repo>` by digest only (untagged, with provenance and an SBOM), smoke-tests that digest, and only then tags it with `docker buildx imagetools create`, so the published image is the tested one; a failed test leaves an untagged digest. Tags: `main`, `latest` and `sha-<short>` from `main`, and `1.2.3`, `1.2` and `sha-<short>` from a `v1.2.3` tag. The GHCR package starts private; Azure pulls it with a token that has `read:packages`, or make the package public. To block merges until the checks pass, mark `quality`, `integration` and `image` as required status checks in the GitHub branch protection settings.
